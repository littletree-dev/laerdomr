# 終了コードだけで成否を決めて空振りを見逃す

## 症状 — 何が起きるか

コマンドが終了したことだけで、仕事が完了したと報告する。
空の出力や更新されていない成果物が残っても、定期処理は成功扱いになる。
逆に、成果物が正しくできていても終了コードの解釈だけで失敗とする。

## 実例

- **F-8**：外部コマンドの導入確認で異常な終了コードが見えたが、実際の導入と動作確認は成功していた。コードと実結果を分けた確認が必要だった。
- **F-58**：登録済みの定期タスクが構文エラーで動いていなかった。実行結果を見に行くまで失敗に気づかなかった。
- **F-116**：シェル間で呼出パスが壊れ、終了コードが正常に見えても回答ファイルはできなかった。出力末尾だけを残す処理が、原因を示す出力も隠した。

## なぜ起きるか

呼出側の成功条件が、対象ツールの仕事の完了条件と接続されていない。
出力の短縮やパイプが診断情報と終了状態を隠す。
定期処理では失敗通知だけでなく、実行されないことや成果物が古いことの検出も抜ける。

## 仕組みでの対策

**道具化**：呼出ラッパーに、ツールごとの終了コードの意味、完全な標準出力・標準エラーの保存、成果物の検証をまとめる。成果物は今回の実行専用の場所へ出し、存在・非空・形式・期待内容を満たして初めて成功にする。古い成果物を再利用して合格にしない。

**検査スクリプト・既定値の変更**：失敗、空の成果物、古い成果物、実行されない場合を別々に検出する。定期処理には最終成功時刻と成果物の更新を調べる監視を付け、予定間隔を超えたら通知する。監視自体が動かない場合も別経路から検出する。

```bash
# Bashでの終了状態とログの保存例。成果物の検証は別途必要。
if command_to_run >stdout.log 2>stderr.log; then
  rc=0
else
  rc=$?
fi
printf 'exit=%s\n' "$rc"
# command_to_run は実際のコマンドに置き換える。
```

## CLAUDE.md に書くなら

終了コードはツールごとの意味で解釈し、今回の成果物と期待内容を確認してから完了を報告する。
完全な診断出力を保存し、空振り・未実行・成果物の更新停止を成功にしない。
